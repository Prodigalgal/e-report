# 权限体系 V4：无角色原子授权与资源关系

- 状态：历史决策，已由 `docs/decisions/2026-09-29-organization-scoped-account-administration.md` 替代；仅作授权体系 V4 的实施记录，不再指导当前账号敏感度或同级管理员管理规则。
- 产品候选版本：`5.0.9`（`5.0.0` 至 `5.0.8` 依次因数据库管理驱动缺失/未注册、无关迁移参数、Node 构建链漏洞、WEB Docker context 路径缺陷、历史岗位规则未安全收敛、元数据断言未限定当前 Schema 及新增审计表未纳入 PostgreSQL 归档计划而拒绝提升）
- 适用范围：Backend、WEB、APP、PostgreSQL baseline、MySQL 到 PostgreSQL 转换器
- 替代：`authorization-policy-v2.md`、`authorization-policy-v3.md` 的运行时授权模型

## 决策

运行时授权只由以下事实组成：

1. 用户身份以及唯一所属组织、可选唯一所属部门；
2. 固定代码目录声明的原子权限；
3. 用户持有的单一有效 `PermissionGrant`；
4. 组织树、部门责任和工单参与关系形成的资源可见性；
5. 操作风险、主体敏感度和会话安全策略。

不再使用角色、管理员等级、管理域、账号保护等级、管理主体、独立委托授权、授权审批身份或岗位绑定参与运行时判定。`superAdmin` 是全局唯一系统信任根主体，但仍通过逐项根 Grant 获得权限，不使用 `*` 或业务代码绕过。

岗位模板仅保存一组可复用的权限选择。应用模板会生成或调整独立 Grant；Grant 不记录模板来源，模板修改、停用或删除不会改变既有授权。

## Every action is permission

每个可以独立授予、撤销、审计、改变状态、读取不同敏感数据或进入 API Token 的业务动作必须拥有独立权限码。分页、字典、预检和同一动作的技术子步骤继承主动作权限，不制造技术权限。

权限定义包含：`code`、中文名称、说明、访问模式、`operationRiskLevel`、`principalSensitivity`、是否允许委派、是否允许进入 API Token、是否为系统级权限。权限定义不包含组织、部门、数据范围、角色或岗位模板。

`operationRiskLevel` 控制二次确认、重新认证和审计强度；`principalSensitivity` 只用于识别横向保护对象，两者不得互相推导。

## Grant 契约

同一用户与权限码只能有一个 ACTIVE Grant。Grant 包含有效期、`grantOption`、`parentGrantId`、授予人、发行类型、状态和完整审计时间，不包含岗位、数据范围或资源关系。

状态为：

- `ACTIVE`：本地有效且上游链有效；
- `SUSPENDED_UPSTREAM`：本地仍保留，但上游暂时不可用；
- `EXPIRED`：本地有效期结束；
- `REVOKED`：被显式撤销；
- `REPLACED`：被新版本 Grant 覆盖。

调整通过“旧记录 REPLACED + 新记录 ACTIVE”实现。兼容的下游授权迁移到新父 Grant；缩短有效期或取消 `grantOption` 时必须预览受影响子树并显式选择级联策略。上游临时恢复可自动恢复下游；撤销、过期和永久替换后的下游只能经过预检重新挂接。

授予权限必须同时具备 Grant 管理动作权限、同一原子权限的有效 Grant 和 `grantOption`，下游有效期不得超过上游。授权深度不设上限，但禁止环。

## 组织、部门和工单数据面

用户始终只有一个所属组织；工单始终只有一个当前归属组织。上级组织自然访问下级组织数据，同级组织默认互不可见。权限码和 Grant 均不携带组织范围。

部门属于组织内部协作结构，可形成树。部门不是租户或通用数据隔离边界，只承担提单、当前责任、历史责任、验收、通知和统计语义。

工单查询需要同时满足原子权限和资源关系：工单归属组织位于用户组织子树，或用户组织因历史归属/完整移交获得保留查看关系。工单被领取或派给具体人员后，其他拥有查看权限且满足资源关系的用户仍可查看详情。

完整移交采用目标组织接受/拒绝的两阶段流程。接受前归属组织不变；接受后目标组织成为唯一归属组织，原组织保留查看关系。

## 横向保护

持有任意有效 `SENSITIVE`、`CRITICAL` 或 `SYSTEM` 权限的用户是横向保护对象，但不因此产生角色或等级。

同组织用户不能修改受保护对象的登录标识、联系方式、密码、状态、会话、受信设备、组织、部门及不属于自身授权链的敏感 Grant。某个 Grant 的上游授予人只能治理其授权链中的具体 Grant，不能接管目标账号。严格上级组织仍需持有对应原子权限；市公司根组织受保护用户由 `superAdmin` 治理。

## API Token

API Token 创建是显式权限动作。Token 权限必须同时满足：创建者当前有效持有、目录允许进入 Token、Token 有效期不超过来源 Grant。Grant 管理、凭据治理、组织治理、敏感配置和系统级权限默认禁止进入 Token。

## 迁移原则

本次允许破坏性迁移，不保留 V2/V3 运行时兼容层。MySQL 历史链只作为迁移来源；PostgreSQL 使用 V4 最终模型 baseline。转换器必须将有效授权压平为独立 Grant，岗位来源不进入目标库，并在切换前验证权限、用户、组织、工单和授权摘要。
