# 决策：组织范围内的对等账号管理与主体敏感度退役

- 状态：方向已确认；Backend、WEB、APP 与 GitOps 流水线正在形成 `6.0.3` 测试候选，部署测试环境后等待业务验收，验收前不发布生产。
- 日期：2026-09-29
- 影响范围：Backend、WEB、APP、用户导入导出、组织迁移、授权 API
- 关联需求：`docs/requirements/2026-09-29-personal-mcp-integration.md`（MCP 使用个人 API Token；MCP 工具目录替代并移除旧 `GET /ai/guide`）
- 当前候选版本：`6.0.3`；Android `versionCode=5000003`。同一不可变构建先进入测试环境，业务验收通过后再由手动生产流水线提升。
- 替代：`authorization-policy-v4.md` 的“横向保护”规则，以及 V3 对同域同级管理员账号互相管理的禁止规则。

## 背景与目标

原 V3 需求将业务权限、授权委托和账号管理分开，用于限制跨组织操作和超出自身能力的转授权。当前 V4 通过权限目录中的 `principalSensitivity` 计算目标账号最高敏感度；用户获得 `user:manage:create` 等单项权限后，同组织其他管理员就无法修改其联系方式、密码和状态。创建者与其他同级管理员因此不能对等管理目标用户。

本提案以组织关系、每项管理动作的原子权限和授权的 `grantOption` 为主要判定依据。用户由谁创建、由谁首次授权以及目标用户持有哪些业务权限，都不产生账号归属或额外保护等级。管理员重置密码的接管能力、系统签发的基线 Grant 和授权链跨组织失效仍须明确规则，不能用“删除敏感度”一笔带过。

## 管理判定

账号管理动作允许的条件是：同一租户、目标用户位于操作者所属组织或其下级组织、操作者拥有该动作的有效原子权限，并满足该动作已有的领域校验。拥有相同组织范围和原子权限的管理员 A、B 可以对等管理用户 C，也可以按各自权限管理彼此的账号。账号创建者没有专属维护权；新增或扩大授权仍须符合本组织或向下的组织范围。

授权授予、调整、撤销或重新挂接还要求操作者持有相应的授权管理动作权限，以及目标原子权限的有效 Grant 和 `grantOption=true`；授予和调整后的有效期不得超出操作者自身 Grant。A 授予 C 的 Grant，可由与 A 同组织且同样具备转授权能力的 B 管理；B 新授、调整或重新挂接时，其组织也须覆盖 C 所在组织，替换后的 Grant 应挂接到 B 自己的有效父 Grant，并预检下游兼容性。授权链继续记录来源、控制有效性、下游级联和审计，不再充当同组织管理员的独占管理权。

任何授权计划的预览、创建、执行、导入和模板展开，都应在共同入口检查目标租户和组织、本人操作禁令、系统根身份、操作类型权限及对应的 `grantOption`；不能只在某些敏感权限分支校验。`GRANT_PERMISSION`、`ADJUST_PERMISSION`、`REVOKE_PERMISSION`、`REATTACH_PERMISSION` 与模板展开必须使用同一判定。当前 `AuthorizationAdministrationService` 仅在查看入口调用 `AdministrativeControlService`；普通权限新增缺少统一目标组织检查，授权计划写入口也没有共同的本人和系统根检查，实施时须先收敛该入口。

资料修改应按实际字段校验原子权限：姓名等普通资料使用 `user:manage:details:update`，手机号、邮箱使用已有的 `user:manage:contact:update`；组合请求必须同时满足所改字段的权限。当前 `UserService.updateUserDetails` 和导入 `UPDATE` 对联系方式只检查普通资料权限，若移除横向保护而不补上字段级校验，会扩大联系方式修改能力。能力接口和 WEB/APP 按钮应与服务端共用动作语义，状态变更还需按具体目标状态而非笼统的 `UPDATE_STATUS` 判断。

保留现有独立边界：跨租户拒绝；兄弟组织之间不互相管理；通过管理入口对自己执行提权、密码重置、状态、会话和授权控制仍拒绝；`SUPER_ADMINISTRATOR` 系统根账号不能由普通租户管理入口修改。`superAdmin` 的受控恢复与系统身份约束不依赖账号敏感度。

## 转授权的组织方向

按组织位置判定：普通用户签发的 Grant 可以从本组织流向本组织或下级组织，拒绝下级向上级、兄弟组织之间以及跨租户转授权。县公司 A 持有权限 P 和 `grantOption=true` 时，可以将 P 授予本县 B，也可以授予县公司下属组织用户；市公司仍可直接授予县公司用户。授予本组织用户不会仅因组织位置扩大 P 的组织数据范围，但会增加持权人数及可能的下游转授权人。

每次授权仍需操作者持有授权动作权限、该原子权限的有效 Grant 和 `grantOption=true`，目标 Grant 的有效期不得超出父 Grant；给目标继续转授的能力还需 `user:authorization:grant-option:issue`。禁止给自己签发新 Grant，Grant 保留父子来源和级联关系。`GRANT_PERMISSION`、会形成新 Grant 的 `ADJUST_PERMISSION` 和 `REATTACH_PERMISSION` 均检查目标组织位于操作者本组织或下级组织；`REVOKE_PERMISSION` 也须遵守相同的目标管理范围。组织迁移或组织树调整后，既有父子 Grant 仍须满足本组织或向下的关系，不能因为历史上合法就永久有效。

市级根组织内的普通管理员若具有授权动作权限及对应 `grantOption`，也可向同组织用户授权，不必因缺少普通上级而全部交给 `SUPER_ADMINISTRATOR`。这类授权可能覆盖整个租户，预览须展示实际组织范围和下游影响。`SUPER_ADMINISTRATOR` 的系统身份及无父节点的 `SYSTEM_BASELINE` Grant 仍按各自来源规则保护；同组织转授权不能把普通用户 Grant 伪装成系统签发。

当前实现尚未统一：`AuthorizationAdministrationService` 对普通权限的 `GRANT_PERMISSION` 没有共同的目标组织检查，而同组织敏感 Grant 的调整又受敏感度或原授权链限制。实施时所有授权入口和预览/执行须统一检查同租户及本组织或下级组织，既允许同组织授权，也拒绝兄弟组织授权；不引入“账号同级保护”的第二套等级模型。

## 退役主体敏感度

删除 `PrincipalSensitivity`、权限目录的 `principalSensitivity` 映射、用户最高敏感度计算，以及基于敏感度的账号和 Grant 横向拦截。同步删除 Backend DTO、WEB/APP 类型和展示、API Token 选项及用户导出表中的“主体敏感度”列。`operationRiskLevel`、`systemScoped`、`apiTokenAssignable`、原子权限和 `grantOption` 保留，各自继续承担操作风险、系统权限、Token 可分配性和委派边界。

当前敏感度由代码和有效 Grant 计算，`users` 与权限表没有对应的敏感度持久化字段，因此不需要为该属性删除数据库列。公开 JSON 字段、导出列和客户端策略枚举会变化，须按不兼容 API 契约发布。

无需删除敏感度列不代表无需治理数据：上线前应扫描现存 Grant 的来源类型、父子链和当前组织关系，列出不符合新委派边界的授权并制定修复或阻断方案。`PermissionRiskLevel` 仍用于操作风险提示，不得把它重新当作账号等级。

## 密码重置与系统基线

当前 `/admin/users/{userId}/reset-password` 已允许管理员指定新密码，目标账号下次登录须改密，旧会话、API Token 和受信设备信任会被撤销。按本次简化方向，保留这条现有流程，不建设邮箱验证、一次性重置令牌或邮件激活。管理员可管理同组织及下级组织的其他管理员账号，条件仍是持有目标组织范围内的 `user:manage:password:reset`；本人通过管理入口重置自己、跨租户/跨兄弟组织操作和普通管理员重置 `SUPER_ADMINISTRATOR` 仍拒绝。

这一权限的真实含义是：持有人能够以组织范围内任一可重置账号的身份登录，取得该账号的有效权限和 `grantOption`。因此 `grantOption` 只限制直接授权操作，不能保证同组织内已获密码重置权的管理员无法绕过委派边界；管理员的后续操作会显示为目标账号执行，不能只靠业务操作日志追溯最初的重置人。权限目录和“用户凭据管理员”岗位说明应写清该能力，仅向被信任可接管本组织账号的管理员授予。市级根组织的管理范围覆盖整个租户，不能把风险描述成固定的单一区县。重置操作需独立记录操作者、目标、组织、时间和结果，并保留当前的强制改密与凭据撤销；密码和明文请求体不进入日志。

`SUPER_ADMINISTRATOR` 仍由 `systemKey` 保护。另有普通 `User` 持有 `SYSTEM_BASELINE` 根 Grant：启动时 `SystemAuthorizationBaselineInitializer` 根据其当前组织是否为租户根组织，分别重建市级或区县管理员权限。此类系统基线不能当作普通用户 Grant 随意撤销、重新挂接或跨层级迁移；否则下次启动可能自动恢复甚至切换基线。办理系统基线身份的调整须走明确的系统管理流程，或先完成基线退役与普通授权转换，不能复用普通组织迁移的 `KEEP`/`REVOKE_ALL`。`MIGRATION` 根 Grant 的来源也需单独核对；普通管理员替换 Grant 时不能保留已不真实的系统来源类型。

## 组织迁移

组织迁移以办理人的管理范围判定：办理人须在同一租户，对原组织和目标组织都拥有 `user:manage:organization:move` 的有效组织范围。下级管理员不能将用户调出自己的范围；向上调整通常由目标组织或其上级管理员办理。例如县级用户调到市级，由有权管理该县和市级组织的市级管理员办理。当前预览与执行路径已分别校验原组织和目标组织，实施时须保证导入路径也遵守同一规则。

删除依赖敏感度的 `REVOKE_SENSITIVE` 策略。向下移动时，被调用户已收到的权限对应的数据范围缩小；这些 Grant 可在预览后保留或撤销，但被调用户过去向他人转授的 Grant 也必须重新审查。向上或跨分支移动时，同一原子权限对应的数据范围可能扩大或改变，不能仅改变用户组织并沿用下级管理员签发的父 Grant；也不强制撤销全部授权。办理人逐项确认迁移后的授权：保留某项 Grant 须持有同一原子权限的有效 `grantOption`，并通过有效期和下游授权链预检。若原父 Grant 持有人的组织仍覆盖目标组织且授权链有效，可保留原链；否则由目标组织本级或上级的合格管理员将目标 Grant 重新挂接到自己的有效 Grant。迁移办理人若位于目标同组织，仍须有相应授权动作权限与 `grantOption`，不能只凭组织迁移权限处理 Grant。其余 Grant 显式撤销；系统来源 Grant 须走独立规则，不能借普通用户的父 Grant 静默转换来源。`REVOKE_ALL` 只能作为普通可撤销 Grant 的快捷选择，`KEEP` 在向上或跨分支时必须完成逐项预检，不能无条件沿用旧父 Grant。

授权链约束必须双向检查：每一条有效普通用户转授权边的上游持有人当前组织须为下游持有人当前组织本身或其祖先，系统签发的无父节点 Grant 按来源规则处理。用户本人迁移时，检查其收到的 Grant，也检查以其 Grant 为父节点继续签发的下游 Grant。县级管理员移到另一县后，原县下属持有的 Grant 不能继续依赖这个管理员；市级管理员下调到县级时，过去签发给其他县的 Grant 也不能原样保留。逐项预览应支持由具备权限的目标组织本级或上级重新挂接，或明确撤销并展示级联影响。`OrgUnitService.move` 会改变整棵组织树的上下级关系，因此组织节点迁移也须经过同一授权链影响检查；否则只治理用户迁移仍会留下越界链。当前 `PermissionGrantChainService.isEffectivelyActive` 只验证状态、有效期和父子权限一致，不验证父子持有人的组织关系，新规则必须覆盖实时授权计算或提供同等强度的预检、失效和缓存刷新机制。

`user:manage:organization:move` 只授权改变归属，不能自动替代对每项原子权限的 `grantOption`。否则办理人虽不能直接转授某权限，却可通过把已获该权限的用户调到上级组织来扩大其数据范围。迁移前须识别现存 `USER`、`SYSTEM_BASELINE`、`MIGRATION` 等来源和父子链，并在测试环境先计算需要重新挂接、撤销、专门处理的数量；不能以“无敏感度数据库列”为由跳过授权数据核对。

预览应覆盖 `ACTIVE` 和可能恢复的 `SUSPENDED_UPSTREAM` Grant，逐项显示保留、重新挂接、撤销、不可处理、受影响下游用户及其权限变化，并列出未闭环工单和待处理责任。若迁移后当前处理人会失去处理工单所需的权限，预览必须提示先调整责任或明确处理方案。缺少必要的转授权、撤销或授权链兼容条件时，整个迁移失败，不先移动用户或只处理部分 Grant。执行应以迁移后的组织关系重验授权链，在同一事务内锁定或有条件更新目标用户、相关 Grant 和组织版本；仅比较目标 `authorizationVersion` 不足以覆盖其他用户授权、父 Grant 或组织树并发变化。迁移后应失效目标及受影响下游用户的授权快照和旧会话，撤销可能继承更大组织范围的既有 API Token。当前 `CredentialRevocationService.afterSecurityControlChange` 有相应撤销能力，但组织迁移路径没有调用。迁移不自动改派工单。现有单个 `strategy` 字段无法表达逐项决定，实施时需同步设计预览、执行、导入与 WEB/APP 契约。

用户组织迁移应记录独立审计事件：办理人、原因、原/目标组织、授权计划摘要、实际保留/重新挂接/撤销的 Grant、下游影响及执行结果。当前 `OrganizationMoveEvent` 只覆盖组织节点迁移，普通用户迁移仅改 `users.org_unit_id` 和可能的 Grant，`KEEP` 甚至没有 Grant 变更记录；不能把更新时间当作完整审计。

接口只接受 `KEEP` 或 `REVOKE_ALL`。客户端必须使用当前版本和当前工作簿模板；其他策略值直接校验失败，不进行隐式转换。

批量导入 `ORG_MOVE` 目前把撤销操作合成授权行用于预览，同时执行器又先调用 `UserService.updateUserDetails` 按策略处理授权，再执行合成授权行；非 `KEEP` 场景存在重复撤销导致整用户事务失败的风险。新契约须保证每项变更只有一个执行者，并同步升级工作簿模板版本、异步任务预览摘要和旧模板拒绝提示。授权计划与组织迁移预览均应绑定办理人、原/目标组织、授权链和组织树的版本/摘要，执行前重新计算差异；预览后组织树或任何相关 Grant 变化都应要求重新预览。目标组织已停用或其祖先已停用时是否允许迁入，也须形成显式规则；当前直接迁移仅校验组织存在且同租户。

## 验收与回滚

- A、B 同组织且动作权限相同：均可管理 C 的普通资料和状态；C 位于本组织或下级组织时，A、B 可按各自 `grantOption` 为 C 新授、调整、撤销或重新挂接 Grant；联系方式变更须另有 `user:manage:contact:update`。
- 市级 A 可向所辖县 B 或本市 B 授权，县级 A 可向本县 B 或其下属组织 B 授权；县级 A 向市级或邻县 B 授权均拒绝。普通父 Grant 持有人的组织须覆盖目标组织，且该关系在授权时及组织迁移后均有效；预览与执行一致。
- A、B 可按相同规则管理彼此；本人通过管理入口操作自己的高风险账号动作仍拒绝。持有 `user:manage:password:reset` 的管理员可为本组织及下级组织的其他管理员指定新密码；强制改密、凭据撤销和独立重置审计生效，明文密码不入日志。市级管理员的实际范围是整个租户；通过目标身份取得更高 `grantOption` 是该权限被授权时接受的能力。
- 跨租户、兄弟组织、失效或过期 Grant、超期委派、`grantOption=false`、根系统账号均被拒绝；所有授权计划类型和导入通道的预览与执行结论一致。
- 向下迁移须检查被调用户向组织外下游发出的 Grant；上移及跨分支由同时覆盖原组织和目标组织的管理员办理，只有原授权链在目标组织仍满足本组织或向下关系时才可保留，否则由目标本级或上级的合格管理员重新挂接，或明确撤销；迁至市级根组织不自动取得系统基线。
- 系统基线管理员不得通过普通用户迁移变更其基线级别；组织节点迁移也须预检整棵树的授权链；既有 API Token 不得因用户上移继承更大的组织范围。
- 并发修改目标、父 Grant、下游 Grant 或组织树时，执行必须拒绝旧预览；用户组织迁移有独立审计，旧 APP 和旧导入策略不得静默改变授权结果。
- Backend 权限集成测试、WEB/APP 契约与页面测试、导入导出模板测试、版本契约校验和测试环境真实管理员流程通过后，再进入生产发布。

回滚不能只切换上一不可变 Backend/WEB 镜像：新模型已经执行的 Grant 重新挂接、撤销、组织迁移与新客户端 API 契约可能不被旧版本安全解释。切换前保留数据库一致性快照、组织/授权差异和版本匹配的镜像；回退前冻结相关写入，验证旧版本能读取当前数据，并按审计记录恢复业务数据，否则采取向前修复。已安装的 APP 仍按更高 `versionCode` 发布修复版，不能复用旧 APK。
