# ADR：权限体系 V3 控制平面与 PostgreSQL 数据边界

- 状态：已批准，实施中
- 日期：2026-08-20
- 替代：`authorization-policy-v2.md` 中的委派边界和目标账号可管理性判定

## 决策

V3 采用四个互相独立、在服务端组合判定的平面：

1. **业务访问面**：`PermissionGrant` 决定主体可以对哪些业务资源执行什么动作。
2. **授权委托面**：`DelegationGrant` 决定主体最多可以向他人授予什么访问权，以及能否继续转授权。
3. **账号管理面**：`ManagementDomain`、`AuthorityActorAssignment` 和 `SubjectProtection` 决定谁可以管理哪个账号。
4. **风险审批面**：`AdministrativeActionPolicy`、`PrivilegedActionRequest` 和审批事实决定高风险动作是否需要二次认证或职责分离。

岗位权限模板只生成访问授权草案，不参与运行时鉴权，不拥有独立作用范围，也不默认生成委托授权。

权限体系 V3 与 PostgreSQL 迁移作为 V4 的同一破坏性升级交付；`4.0.0`、`4.0.1`、`4.1.0`、`4.1.1`、`4.1.2`、`4.1.3`、`4.1.4`、`4.1.5` 为已占用的迁移测试候选，加入组织迁移预检与差异确认后的当前候选为 `4.2.0`。业务访问、授权委托、账号管理和风险审批仍由应用领域服务判定；PostgreSQL RLS 只承担 `tenant_id` 硬隔离和写入归属校验，作为应用授权之外的第二道防线。

## 安全不变量

- 业务访问权不隐含委托权。
- 数据范围不隐含账号管理范围。
- 管理上下级由管理域祖先关系和账号保护级别决定，不按权限数量、模板名称或用户名推导。
- 同域同级管理员默认不能互相执行凭据、状态、会话或授权管理动作。
- 不允许自我提权、自我审批或降低自身保护级别。
- 委托范围、资源关系和有效期必须受显式上游委托授权覆盖。
- `may_subdelegate` 默认关闭；下发委托权必须拥有该能力。
- 默认管理员账号本身受保护，不仅保护其系统来源授权。
- API Token 不携带委托权和账号控制权。
- UI 只表达结果，所有接口在提交时重新校验。
- 应用数据库角色不是表所有者，不具有 PostgreSQL `BYPASSRLS`；迁移和备份使用独立运维角色。
- RLS 不推导组织上下级、资源关系或原子权限，避免数据库策略和应用授权形成两套真相。

## 管理域与保护级别

管理域依据数据库组织树生成：系统根、租户根、市/县组织域。运行时代码不得写死漳州市编码、区县编码或用户名。

账号保护级别从低到高为：

- `STANDARD`
- `ELEVATED`
- `ADMINISTRATIVE`
- `DOMAIN_OWNER`
- `SYSTEM_ROOT`
- `BREAK_GLASS`

保护级别不授予任何业务权限，只约束账号管理动作。跨区县高权限账号的保护管理域提升到相关范围的最近公共上级。

## 管理动作

账号管理按原子动作判定，不再使用单一 `fullyManageable`：

- 查看资料
- 修改普通资料
- 修改身份恢复信息
- 调整所属组织
- 修改账号状态
- 重置密码
- 撤销会话
- 查看访问授权
- 下发/调整/撤销访问授权
- 下发/撤销委托授权
- 调整保护级别
- 更换管理域所有者

每个动作单独返回 `allowed` 和稳定 `reasonCode`，前端不得根据一个总布尔值推导全部按钮。

## 一致性与缓存

- `User.authorizationVersion` 升级为统一安全版本语义，业务授权、委托权、管理主体、保护、组织、状态和凭据变化都必须递增。
- 业务访问快照与管理控制快照分离缓存。
- 高风险写操作必须在事务中重新加载目标、委托来源、管理域和保护事实，校验版本后提交。
- 管理控制快照不可用时写操作 fail closed。

## 迁移原则

- 保留现有 `PermissionGrant` 作为访问事实。
- 根据组织树和 `defaultAdministratorUserId` 生成管理域、管理主体和账号保护。
- 只按内置、可审计规则生成初始委托授权，禁止从所有现有访问权限直接推导。
- `SYSTEM` 来源仍不可由普通用户撤销，但账号保护改由 `SubjectProtection` 统一执行。
- V3 API、WEB、APP 和导入导出完成切换后删除 V2 委派与 `fullyManageable` 判定，不保留长期兼容分支。
- PostgreSQL 使用原生 `uuid`。MySQL `BINARY(16)` 按现存原始 16 字节映射，不对历史 `UUID_TO_BIN(..., 1)` 记录统一反交换。
- 旧 MySQL Liquibase 链冻结为历史，PostgreSQL 从当前最终领域模型建立 `4.0.0` baseline；以后简单结构使用可移植变更，数据库特性使用显式 `dbms:postgresql` 变更。
- 目标运行时只保留 PostgreSQL Driver；MySQL Driver 仅允许存在于隔离的数据迁移工具中。
- 不使用应用双写。测试演练和生产切换采用停写、终态备份、转换、校验、切换、开放写入的顺序。

## 取舍

不引入外部策略引擎。当前单体 Spring Boot、PostgreSQL 和 Redis 足以承载该模型；显式领域服务、数据库约束、租户 RLS 和可测试决策对象比新增分布式依赖更容易保证一致性与可运维性。迁移 PostgreSQL 的目标是收敛 UUID、约束、索引和租户隔离契约，不以“更换数据库必然提速”为前提。
