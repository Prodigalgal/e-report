# ADR：使用能力闸门、窄角色和可自定义岗位模板构建管理权限

- 日期：2026-08-09
- 状态：已接受，扩展已投产
- 替代：`admin-management-plane-boundary.md` 中“必须依赖 `ROLE_ADMIN` 进入管理平面”的判定

## 决策

系统使用三层授权模型：原子权限描述最小动作，窄角色描述单一岗位职责，数据范围描述动作可以作用的组织边界。管理平面不再由角色名或任意业务权限推断，而由固定权限 `management:access` 统一控制；具体页面和接口继续校验各自的动作权限。

市公司、区县和平台管理员角色改为身份标记。管理员账号通过多个窄角色组合获得完整能力，身份角色本身不再聚合几十项业务权限。

“快捷岗位模板”不是写死在前端的数组，也不是新的授权主体。系统使用租户隔离的 `role_bundles` 和 `role_bundle_roles` 保存组合：内置模板由固定目录同步且只读，自定义模板可增删改、停用和复制。应用模板时将角色集合展开为用户明确授权；模板后续变化不追溯修改既有用户。

## 原因

- 角色名适合表达身份，但不能稳定表达不断扩展的管理能力；使用 `ROLE_ADMIN` 硬编码会阻止专职查看员或模块管理员进入其工作台。
- 使用“拥有任意工单权限”推断管理员会把一线提单者和处理人员错误提升到管理界面，已经在生产账号上复现。
- 一个超级管理员角色使权限审查、区县差异化授权和最小权限分配不可解释，权限变更也会扩大所有管理员的影响面。
- 原子权限、职责角色和组织范围分别变化，三者分离后可以独立扩展，并继续复用现有 Spring Security 与 `DataScope`。

## 访问模式

权限目录将动作分类为 R 或 W，角色根据有效权限自动计算 `NONE`、`R`、`W`、`RW`。访问模式是可审计的派生结果，不在数据库重复存储，避免角色权限调整后元数据漂移。

人工岗位默认提供 R 或 RW 角色。W-only 仅作为自定义组合或自动化账号的表达能力，不作为需要读取上下文的内置人工岗位模板。

## 授权顺序

```text
认证账号
  -> management:access 决定能否进入管理平面
  -> endpoint permission 决定能否执行具体动作
  -> DataScope 决定动作能覆盖哪些组织和数据
  -> 领域状态机决定当前对象是否允许该动作
```

任一层失败都返回 403 或领域冲突，前端隐藏不能替代后端校验。

## 数据迁移

- 为每个租户创建窄读取角色和窄读写角色。
- 将现有 `ROLE_ADMIN`、`ROLE_COUNTY_ADMIN`、`ROLE_PLATFORM_ADMIN` 的直接角色和范围授权复制到预定义组合角色。
- 保留身份角色及原授权记录，便于通知收件人解析和管理身份展示；仅收窄其权限为 `management:access`。
- 递增受影响用户的 `authorization_version`，清除 Redis 鉴权快照并使旧令牌失效。
- 不删除自定义角色，不更改现有非管理员用户授权，不改变任何工单归属或生命周期数据。
- 新建岗位模板表并同步内置模板；租户自定义模板只由租户内具备 `role-bundle:manage:*` 权限的人员维护。

## 结果

- 业务角色不能因工单查看或处理权限进入管理后台。
- 专职模块角色可以进入管理后台，但只能访问其模块。
- 市、区县管理员保留用户可理解的身份，同时其能力可以逐项审计、增删和按组织授权。
- 新增管理模块时必须显式选择入口权限、动作权限和数据范围，不会自动扩散给所有工单角色。

## 回滚

权限迁移属于授权契约切换，不保留长期双轨。发布失败时恢复迁移前数据库快照及上一版本应用；只回滚前端或只回滚后端会造成权限表现不一致，不作为允许的生产回滚方式。
