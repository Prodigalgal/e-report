# ADR：用户管理原子保存与单角色单 Grant

- 日期：2026-08-10
- 状态：已接受，已实施

## 决策

用户列表只提供查询、新建、删除、恢复和进入详情。资料、账号状态、角色及数据范围集中在用户详情页维护，并由 `PUT /admin/users/{userId}/detail` 在一个数据库事务内原子提交。

每个租户内，同一用户与同一角色只允许存在一条 `MembershipRoleGrant`。数据库唯一约束为 `(tenant_id, membership_id, role_id)`；历史重复记录由 Liquibase 020 选择最宽有效范围后收敛。客户端必须拒绝重复角色，并校验服务端回传 Grant 与提交内容一致。

用户详情的工单绩效采用租户限定的只读聚合投影，按目标用户即时统计，不把统计值持久化，也不改变工单生命周期数据。

## 原因

- 旧页面依次调用资料、状态和角色三个接口，中途失败会形成部分保存，且成功提示无法证明最后的授权结果。
- 客户端按“一个角色一个范围”编辑，而历史迁移允许同一角色多条范围，导致取消勾选后再次读取仍出现旧授权。
- 将编辑迁入详情页，可以同时呈现身份、授权和业务效率，列表保持适合快速检索的密度。

## 权限与失败行为

- 读取详情要求 `user:manage:view`；统一写接口还要求至少一个用户写权限。
- 服务层对 `details`、`status`、`roleGrants` 分别再次检查对应权限与组织范围，拥有某一写权限不能修改其他字段。
- 任一校验、权限或持久化失败均回滚整个请求；客户端保留表单内容并显示明确错误，不显示成功提示。
- 已删除用户只能查看，恢复仍使用独立显式操作。

## 兼容与回滚

- 旧的分项 API 暂时保留给既有调用方，但 Web 与 Android 1.0.39 不再使用它们进行编辑。
- 020 的唯一约束是新写入契约。若必须回滚应用，应优先回滚到仍兼容单 Grant 的上一版；恢复数据库备份是撤销历史范围收敛的唯一完整方式。
