# ADR：登录态位置采集与隐私边界调整

- 日期：2026-11-14
- 状态：已接受
- 取代：`docs/decisions/lightweight-client-observability.md` 中"不采集原始经纬度、详细地址"的约束在**登录态定位**这一场景上的适用性

## 背景

项目在 5.1.2 与 5.3.2 两版建立了轻量客户端可观测性，并把"不采集原始经纬度、详细地址、IMEI、MAC、Android ID 或设备序列号"写入决策与需求文档，同时用 `ObservationDataSanitizer` 在服务端强制脱敏坐标与地址。

新的运维需求要求管理员掌握在岗人员分布，以支撑工单派单与调度：后台需要展示已登录用户的位置与设备详情，并在同一张地图上叠加工单故障点；APP 需持续上报登录用户位置。

这直接抵触既有边界，必须显式决策，而不是绕过脱敏实现。

## 决策

**在登录态定位这一特定场景放行坐标采集，同时保持既有观测通道的脱敏约束不变。**

### 放行依据

- 采集对象为**公司配发的办公手机**，非员工私人设备。
- 入职劳动合同已包含定位条款；用户确认无需在应用内额外告知。
- 用户实行轮班制且工时弹性，"仅工作日"或"仅上班时段"的限制规则不适用。
- 用途为企业内部生产管理（工单派单、人员调度），非行为监控或绩效考核画像。

### 采集边界（不可放宽）

- 仅在**登录态且前台服务运行**时上报；退出登录立即停止。
- 只保存**最新位置**，不保留历史轨迹，不提供轨迹回放。
- 位置数据仅对持有 `user:session-location:view` 权限的账号可见，该权限仅分配管理员。
- 位置链路与观测通道**物理隔离**：不复用 `client_observation_events`，不放宽 `ObservationDataSanitizer`，坐标与地址不进入观测事件。
- 写入运行日志时坐标仍需脱敏。

## 关键取舍

- **选择新建独立链路而非复用观测通道**：观测表已按租户分区、有保留期与脱敏管线，复用看似省事，但会让"放宽脱敏"成为隐式副作用，且观测表的写入路径是有界缓冲 + 批量落库，语义是事件流而非"当前状态"。位置是**状态**（每会话一行、可覆盖），与事件流模型不匹配，独立建列更贴切且查询更廉价。
- **选择只存最新位置而非轨迹**：需求描述的是"当前已登录用户情况"，地图展示当前态势。轨迹会让数据量与隐私敏感度线性增长，且需要额外的保留期与清理机制。数据模型预留扩展点，确认需要时再单独评估。
- **选择接口统一返回 GCJ-02**：高德渲染必须用 GCJ-02，若返回 WGS84 让前端转换，每个消费点都要重复转换逻辑且容易漏。接口层统一转换并在字段标注坐标系，把转换收敛到一处。工单存储仍保持 WGS84 契约不变。
- **坐标系识别不做静默猜测**：WGS84 与 GCJ-02 仅相差约 500 米，落在同一城市内难以可靠区分。强行猜测会让用户报出看似正确但偏移数百米的坐标。改为给出候选与置信度、由用户确认，并在界面上展示转换前后对比。
- **保留权限门控（用户曾表示可不加）**：不加门控意味着任何登录账号都能查看全公司同事的实时位置，这是实质性的越权面扩大。挂独立权限点不增加管理员的使用成本，但能挡住普通账号互相查询位置。

## 结果

- 管理员可在后台地图上掌握在线人员与故障点分布，缩短派单决策链路。
- 报单不再依赖用户自行填写标准不一的经纬度，减少因坐标系混淆导致的定位偏差。
- 既有隐私边界在其余场景（操作轨迹、故障诊断）继续生效，脱敏管线不退化。
- 后续若监管或合同条款变化，撤销点明确：关闭上报接口 + 停止前台服务 + 清空位置列，不影响其他能力。
