# v5.6.8 媒体脱敏运行时依赖修复任务规格

## 目标

在测试环境发现 v5.6.7 的 `cv2` 导入还缺少 `libgthread-2.0.so.0` 后，补齐 `libgl1` 与 `libglib2.0-0` 运行库，确保 RapidOCR worker 能在 slim 基础镜像中稳定启动。

## 范围

- 只调整媒体 worker 的 Debian 运行时依赖；品牌识别、OCR 目标、异步队列和数据契约保持不变。
- Backend、WEB、APP、数据库迁移、镜像和发布记录统一使用 `5.6.8`，Android `versionCode=4006008`。
- 重新执行本地测试、供应链审计、镜像构建、测试环境 rollout 和生产晋级验收。

## 验收标准

1. media worker `Ready`，日志无 `libGL.so.1`、`libgthread-2.0.so.0` 或 OCR 初始化异常。
2. 测试环境后端、WEB、媒体 worker 全部使用同一不可变 v5.6.8 镜像标签，数据同步 CronJob 保持暂停。
3. 正负样本回归、入口 smoke、迁移与权限/附件回归通过后，生产环境才切换。

## 实施结果

- 运行时依赖链固定为 `opencv-python -> libgl1 + libglib2.0-0`，未引入 headless 浏览器或重量级观测组件；worker 镜像启动、`cv2` 导入和 RapidOCR 初始化均已在测试环境验证。
- 发现生产首批历史图片处理时 512Mi 内存限制不足（容器被 `OOMKilled`，exit 137），未改变图像处理逻辑和并发度；测试、生产清单统一调整为 `requests.memory=256Mi`、`limits.memory=1536Mi`，保持单 worker、单任务串行处理。
- 调整后测试环境重新处理 1 个真实同步样本，状态由 `QUEUED` 到 `READY`，`attempt_count=2`，worker 重启 `0`；生产 worker 连续处理历史队列，观察到峰值 `VmHWM=1112236 kB`，在 1536Mi 限制内，重启 `0`。

## 运行约束

- 只保留原图到上传目录、脱敏结果写入 `_sanitized`；不删除原始材料。
- 仍以 `IMAGE_REDACTION_MAX_PIXELS`、`IMAGE_REDACTION_MAX_SIDE` 和文件大小上限作为输入边界；若后续生产出现接近 40MP 的极端图片，应先扩容节点或单独优化峰值内存，不通过提高并发度规避。
