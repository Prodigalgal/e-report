# 2.5.3 权限目录漂移与默认管理员修复

## 目标

- 固定代码目录作为原子权限唯一展示来源，历史数据库权限行不得阻断岗位模板页面。
- 对代码目录缺失、数据库遗留、引用中退役权限建立分级校验、结构化告警和只读诊断。
- 使用 Liquibase 050 幂等治理无引用退役权限；有引用权限只允许按明确的一对一决策迁移，禁止一对多自动扩权。
- 将默认管理员身份与组织显式关联，统一维护全局超级管理员、市公司根组织和区县/非根组织默认管理员的当前内置岗位版本。

## 范围

- Backend：`PermissionCatalog`、权限目录查询、目录漂移扫描与诊断、默认管理员岗位维护。
- Database：当前权限目录发布清单、迁移审计、组织默认管理员关联、历史默认账号回填、退役权限清理。
- 权限事实：`authorization_profile_permission_rules`、`permission_grants`、`api_token_permissions`。
- 版本：Backend、WEB、APP 和部署清单统一升级至 `2.5.3`；无前端业务页面改动。`2.5.1`、`2.5.2` 测试候选因逐步发现历史空授权与被复合岗位覆盖的冗余标准 Grant 而废弃。

## 非目标

- 不在管理页面提供权限删除操作。
- 不自动展开一对多权限映射，不改变未知引用的授权语义。
- 不把区县管理员提升为全市 SLA 编辑员；区县默认岗位继续只读 SLA。
- 不清理用户主动增加的直接授权、定制权限或不属于默认管理员组件的岗位。
- 不再通过 `app.bootstrap-admin.*` 创建、重置或识别根租户管理员；仅保留 `app.bootstrap-super-admin.*` 作为全局唯一超级管理员的首次引导入口。

## 关键规则

1. `PermissionCatalog.entries()` 决定权限名称、中文名、说明、访问模式、风险等级和资源关系；数据库只提供持久化 UUID 与外键目标。
2. Liquibase 先把当前发布目录补齐到数据库；迁移结束后若代码存在、数据库仍缺失，则属于致命不一致，应用拒绝启动。
3. 数据库存在、代码缺失属于遗留漂移：运行时隐藏并告警；有引用时标记为严重，但不自动删除。
4. 退役权限候选由“数据库权限码减当前发布目录清单”确定；历史映射表不能单独判定退役状态。
5. `api_token_permissions` 按实际 `permission_name` 字段迁移。
6. 根组织默认管理员使用 `TENANT_ADMINISTRATOR` 和租户全域；非根组织默认管理员使用 `COUNTY_ADMINISTRATOR` 和本组织树；超级管理员额外使用 `PLATFORM_ADMINISTRATOR`。
7. 默认管理员岗位维护只替换内置岗位生成的标准权限；直接授权和定制授权必须保留。发生实际变化时只递增一次 `authorization_version`。
8. `users.system_key` 只保留 `SUPER_ADMINISTRATOR`；根租户 admin 与所有下级默认管理员均由 `org_units.default_administrator_user_id` 识别，启动配置优先级不再高于数据库关系。

## 验收标准

- 插入无引用未知权限后，`GET /api/admin/permissions` 返回 200 且不展示该权限。
- 未知权限详情返回 404；日志不再出现 `Permission is not part of the fixed catalog`。
- 当前代码目录缺少数据库行时启动失败，并明确列出缺失权限码。
- 漂移诊断返回数据库独有、代码独有、三类引用数量和严重等级；扫描结果未变化时不重复刷告警。
- Liquibase 050 首次执行和重复执行均成功；无引用旧码被删除，有引用一对多旧码使迁移失败且不改变权限事实。
- 平台、市公司根组织、11 个区县默认管理员均关联到明确组织并拥有对应当前标准岗位；自定义授权保留，旧会话失效。
- `nanjing` 可修改本组织邮件发件方、查看 Redis 诊断、查看但不能修改 SLA。
- MySQL 8.4 迁移、Backend 全量测试、三端版本契约、测试环境真实登录 smoke 全部通过。

## 发布与回滚

- 发布前备份 `permissions`、三类引用表、授权岗位/授权事实、用户授权版本和组织默认管理员关系。
- 应用与 Liquibase 050 同版本发布；先测试命名空间完整演练，再生产备份、迁移和切换。
- 代码回滚不恢复已确认退役的零引用权限；只有迁移验证错误时依据备份精确恢复。
