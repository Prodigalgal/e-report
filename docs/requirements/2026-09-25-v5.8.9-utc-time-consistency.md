# 5.8.9 UTC 时间读写一致性

## 目标

延续 5.8.4 展示契约：数据库和 API 的 `LocalDateTime` 表示 UTC，所有面向用户的时间与按日统计采用 `Asia/Shanghai`（UTC+8）。后端写入、查询和任务执行不依赖主机或数据库会话的默认时区。

## 范围与影响模块

- Backend 时间生成：业务写入统一使用 `UtcTime.now()`；Hibernate 自动时间戳在 UTC JVM 中生成，数据库连接会话固定 UTC。Docker、`bootRun` 和测试 JVM 从启动时使用 UTC；其他启动方式若未固定 UTC，应用启动失败。`LocalDateTime` 按无时区 UTC 字段读写，避免 JDBC 对字段做二次偏移。
- Backend 日期读取：工单日期筛选与每日统计把北京自然日转换成 UTC 半开区间；SLA、授权和保留期仍按 UTC 时间点计算。
- 用户批量治理：Excel 中的授权生效和到期时间按北京时间解释，落库存 UTC；模板标明输入时区。
- WEB、APP：沿用现有统一格式化入口和北京墙上时间输入转换；同步发布候选版本号为 5.8.15。
- 涉及 `time`、工单查询、用户导入、运行配置以及三端版本文件。

## 非目标

- 不修改历史数据库时间数据或表结构；当前数据按已有 UTC 约定读取。
- 不改变 API 字段名称、类型及无时区 `LocalDateTime` 的 JSON 形状。
- 不修改机器用的 `Instant`/epoch 时间及观测事件的 UTC 时间语义。
- 不对生产数据执行批量回填或历史时间修正。

## 验收与验证

- 主机处于非 UTC 时区时，新写入的业务时间与真实 UTC 时间点一致；PostgreSQL 和旧 MySQL profile 的连接会话均以 UTC 执行数据库默认时间戳。
- 北京时间 `00:00` 至 `07:59:59` 的工单在筛选与按日统计中归入正确自然日，跨日边界采用前闭后开区间。
- Excel 中的 `yyyy-MM-dd HH:mm:ss` 和仅日期授权时间回写 UTC 后在 WEB/APP 展示仍是原北京时间。
- 运行 Backend 测试、WEB 测试/lint/build、APP 测试/typecheck、版本契约校验；记录无法覆盖的运行态验证。

## 验证记录

- 2026-09-24 的 5.8.6 源码验证：Backend 在宿主 `JAVA_TOOL_OPTIONS=-Duser.timezone=America/New_York` 条件下执行全量测试，363 项通过，`bootJar` 构建成功；WEB 的 `npm test`、`npm run lint`、`npm run build` 通过；APP 的 `npm test`（63 项）、`npm run typecheck` 通过；时间转换测试在 `TZ=UTC` 和 `TZ=America/New_York` 均通过。
- 5.8.6 的 GitHub 安全工作流因新发布 workflow 的 ShellCheck 警告失败，该候选未构建镜像或部署；5.8.7、5.8.8 在补齐目标机器运行配置与 Secret 迁移前取消。5.8.9 使用拆分后的 GitOps 配置与 Android 自动发布，但安全工作流发现 Backend Netty 4.2.16.Final 和 Bouncy Castle 1.84 的新漏洞，因此未部署。
- 5.8.10 将 Backend Netty 升至 4.2.17.Final、Bouncy Castle 升至 1.85；Android `versionCode=4008010`。构建工具依赖的四条新增告警仅命中 Android Unified Test Platform 内部配置或验证元数据，均未进入 APK release runtime；更新了经复核的 OSV 构建工具基线。
- 5.8.10 的 GitHub 三端构建和 Backend 测试通过，但全量历史容器清单扫描因旧 MySQL、Redis、构建器等镜像的新增或过期例外失败，未部署。5.8.11 将推送发布的容器门禁限定为 Backend/WEB 实际使用的 Temurin/Nginx 基础镜像，计划任务仍扫描全量清单；两个发布镜像构建时要求安装已修复的 Alpine `libexpat`，WEB 另要求已修复的 `libuuid`。Android `versionCode=4008011`。
- 5.8.11 的安全门禁通过，GitHub 成功构建 Backend/WEB 镜像；发布 workflow 的全局并发组被随后完成的 PR 审计触发，取消了仍在构建的 Android job，未提升配置。5.8.12 按用户要求拆分独立的 Backend、WEB、APK 构建 workflow；发布 workflow 等待同一提交的三份制品并核对摘要后自动提升，`versionCode=4008012`。
- 5.8.12 的安全门禁和 Backend/WEB 独立构建成功；Android 原生构建发现两份 Maven POM 未登记在 Gradle 依赖校验元数据，因严格校验而停止。5.8.13 登记从 Maven Central 获取并比对 SHA-1 的两份 POM SHA-256，继续使用严格依赖校验；`versionCode=4008013`。
- 5.8.13 的三端静态验证和 Backend/WEB 构建成功；Android 编译到资源合并阶段时发现校验元数据仅记录 Windows 版 `aapt2`，Linux runner 的同版本 JAR 未获登记。5.8.14 增补从 Google Maven 获取并比对 SHA-1 的 Linux JAR SHA-256，保持严格依赖校验；`versionCode=4008014`。
- 5.8.14 的 Android `assembleRelease` 完成 623 个任务，但发布校验脚本未从 Linux `apksigner` 输出读取到固定文案形式的证书摘要，未上传 APK、未提升配置。5.8.15 改为使用 `--print-certs-pem` 提取唯一签名证书，由 X.509 证书计算 SHA-256 并继续比对生产证书指纹；`versionCode=4008015`。

## 兼容与回滚

- 不迁移历史 UTC 数据；旧客户端仍按原 API 形状读取。升级前需确认自建 API 调用方提交的无偏移时间按 UTC 解释。
- 回滚时恢复上一不可变 Backend/WEB 镜像与 APP 的更高修复版本；数据库无回滚脚本。已用旧逻辑误写为本地时间的历史记录需独立识别，不能批量盲改。
