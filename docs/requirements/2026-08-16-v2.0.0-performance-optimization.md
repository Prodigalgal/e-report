# 2.0.1 性能优化专案

## 目标

以真实用户路径而不是单个函数耗时为准，定位并优化 WEB/APP 登录、首页、工单查询与详情、管理仪表盘、用户与授权管理、用户导入导出等高频链路。每项优化必须提供优化前后同口径数据，并保持权限、租户、数据一致性和安全策略零退化。

## 范围

- 客户端：首屏资源、路由分包、请求瀑布、重复请求、列表渲染、缓存恢复和大文件传输。
- 网关与网络：TLS/HTTP、压缩、静态缓存、请求体缓冲、连接复用和真实客户端地址处理。
- 认证授权：挑战生成、客户端 PoW、密码验证、登录并发门禁、授权快照与会话校验。
- 后端：高频 Controller/Service 调用链、事务范围、序列化、线程池、批处理和缓存命中。
- 数据：SQL 计划、索引、分页、N+1、连接池等待、MySQL statement digest 与 Redis 延迟/命中。
- 运行态：Pod CPU/内存/重启、JVM GC/线程、MySQL/Redis 资源和错误率。

## 非目标

- 不引入 Prometheus、Grafana、APM Agent 或新的重型基础设施。
- 不用降低 Argon2id/BCrypt 成本、验证码、接口验签、限流、权限判定或租户隔离换取性能。
- 不在生产环境生成工单、通知、用户授权或批量导入数据；未经用户批准不切换生产。
- 不以没有调用证据的全局缓存、反规范化或大范围架构重写代替热点优化。

## 基线场景

| 场景 | 测试方式 | 主要指标 |
| --- | --- | --- |
| 公开入口 | 外部 HTTPS 重复 GET | DNS、TCP、TLS、TTFB、total、压缩与缓存头 |
| 登录 | challenge + PoW + login + csrf | 客户端 PoW、服务端登录、总耗时、并发排队与错误率 |
| 会话恢复 | `GET /auth/me` + csrf | warm/cold p50、p95、p99 |
| 工单 | search、详情、事件、附件元数据 | p50、p95、SQL 次数、扫描行数 |
| 管理看板 | scopes + statistics | cold/warm、缓存命中、并发退化 |
| 用户治理 | users、org-units、profiles、用户详情 | 首屏请求瀑布、p95、查询计划、响应体大小 |
| 导入导出 | 预检、任务查询、Range/整包 | 吞吐、峰值内存、任务恢复、下载速度 |

## 首轮 SLO

- 公共 HTML 外部访问 p95 不高于 500ms；同地域网络抖动单独记录，不与服务端耗时混算。
- `auth/challenge` 服务端 p95 不高于 150ms；登录服务端 warm p95 不高于 1500ms，测试环境短时并发下无 5xx。
- `auth/me`、组织目录和岗位模板目录 warm p95 不高于 250ms。
- 用户列表、工单列表 warm p95 不高于 500ms；管理统计 warm p95 不高于 600ms。
- 只读核心 API 在并发 20、持续 60 秒时错误率低于 0.1%，连接池不出现获取超时，Pod 不重启。
- SQL 单次超过 500ms 必须说明；可控高频查询不得出现逐行 N+1；Redis p95 低于 20ms。
- WEB 首次主 JS gzip 继续下降，页面切换不能因重复目录请求产生明显瀑布；大列表不得一次渲染不可控节点。

## 测试数据与安全边界

- 压测目标固定为 `e-report-test`，通知、日报、R2、Outbox 开关保持关闭，数据同步 CronJob 保持暂停。
- 公开和只读 API 可以并发压测；登录只使用测试管理员并限制并发，允许产生可清理的测试会话和短期 Redis challenge。
- 不调用创建/派单/回单/验收/授权变更/通知等写接口；导出只生成 24 小时临时文件。
- 每轮记录镜像、数据库 migration、时间窗口、并发、样本量、客户端网络和 Pod 资源，确保结果可复现。

## 验收与回滚

- 所有改动运行相关单测、后端全量测试、WEB/APP 测试与构建；涉及 SQL 的变更必须使用 Liquibase 并在 MySQL 8.4 验证执行计划和幂等。
- 候选仅部署 `e-report-test`，同口径复测至少三轮；收益不稳定或引入错误、资源尖峰、缓存不一致时撤销该项优化。
- 回滚点为性能候选前的 `20260816-v2.0.0-user-transfer-hardening-test-2`；数据库优化优先新增可回滚索引，不做不可逆数据改写。
