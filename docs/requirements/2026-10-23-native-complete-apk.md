# Native 完整安装包与 OTA 发布契约

## 目标与边界

- 下载中心的最新 Native APK 必须内置当前已发布业务代码；清空应用数据、断网首次启动即为该版本，不通过首次 OTA 补齐。
- Native 的 APK `versionName` 与业务版本一致，`versionCode` 继续按 SemVer 公式严格递增。新的业务候选重新构建完整 APK；只能复用同一源码、同一版本的不可变 APK。
- 原生兼容运行时与安装包版本分离；兼容 JS 更新继续服务已安装的旧 APK，原生能力不兼容时要求安装新 APK。Lite 保持独立 WebView 壳身份及现有更新策略。
- 本次占用向后兼容功能候选 `6.11.0`，先通过自动流程进入测试环境并验收。已上线生产 Backend/WEB、Lite、OTA 保持当前发布；不符合本契约的 6.8.2 APK 上传已停止。

## 实现范围

- Native 运行时契约、版本工具、兼容指纹、完整 APK 封存及制品收集校验；消除将旧 APK 包装成新业务候选的复用路径。
- 原生启动请求附带真实 APK 内置版本，Backend 只对落后的兼容安装提供更新；同版本/更高版本返回 Expo 协议 204，签名回退指令保留独立规则。
- APK 内置清单、真实 Android 版本、源码 SHA、业务版本、签名与摘要共同验证。工作流仍使用 GitHub Actions 构建和发布、私有 GitOps、Argo CD 自动同步。
- APK job 最长 180 分钟、上传与分发步骤最长 160 分钟，保留现有分片重试与 20 分钟对象同步上限。该预算覆盖已观测到约三分钟一个 2MB 分片的网络条件；不把慢速传输视为已发布成功。
- 沿用既有安装包升级、OTA 签名/环境隔离、权限、原生 API 与 Lite 构建，不增加发布组件或手动集群操作。

## 验收与测试

1. JS 业务版本增加时生成该版本的新 Native APK，禁止接受其他源码的旧包；APK Android 版本及内置业务元数据均对应当前候选。
2. 最新 APK 清空数据后断网启动显示当前业务版本；联网后同版本 OTA 返回 204，不下载或应用重复更新。
3. 旧兼容 APK 获取并验证新 OTA；已运行相同 OTA 不重复下发。错误签名、错误环境/运行时和资源失败继续拒绝更新；不可用时保留可运行内容。
4. 新的兼容运行时不会错误强制所有兼容用户重新安装；不兼容安装继续通过现有 APK 更新入口升级。
5. 版本、制品、防止重复 OTA、发布顺序与失败边界回归通过；运行相关 Backend、APP、发布工具测试，版本/指纹/供应链检查；通过 Android 模拟器验证实际安装包。

## 兼容与回退

- OTA 新增可选内置版本请求头；没有该头的已安装客户端保持既有协议行为。运行时仍执行兼容匹配与签名校验。
- 不覆盖已发布 APK、版本号或对象。失败候选不提升生产；Backend/WEB 可恢复上一组不可变镜像，APP 修复使用更高版本。
- 运行时含义参考 Expo 官方说明：https://docs.expo.dev/eas-update/runtime-versions/ 。
