# 双 Android 客户端与 Expo OTA

## 目标

保留现有 RN/Expo 原生客户端 `com.mnnu.ereport`，新增 Kotlin/系统 WebView 薄壳客户端 `com.mnnu.ereport.lite`。原生版接入签名 OTA，减少兼容 JS 更新所需的 APK 覆盖安装。新增能力使用候选 `6.8.0`，先经自动测试发布，生产提升继续等待验收。

## 范围与非目标

- Lite 独立 Gradle 工程、应用身份、图标/名称、签名 APK、更新查询、R2 下载入口与 Actions 流水线；业务页面复用现有 WEB。
- 发布中心新增客户端类型 `NATIVE` / `LITE`，版本唯一键、查询、对象路径和下载按客户端隔离。既有未提供客户端类型的 API 默认 `NATIVE`，已安装原生客户端继续工作。
- Expo 原生包启用 `expo-updates`，由 Backend 提供 Expo Updates 协议、R2 保存不可变 JS/资源，CI 生成并签署 manifest。更新包须经过原生兼容匹配及签名校验。
- 保留测试/生产选择、HTTPS 自定义地址、会话隔离、错误恢复、现有授权与设备能力；更新环境与业务环境一致。
- WEB/APP 发布管理与下载入口支持两款 APK；OTA 显示当前业务版本、原生基础包版本及更新状态。
- 不迁移 Expo/RN 主版本，不替换现有原生版，不新增外部 EAS SaaS 依赖，不手工改集群或绕过既有安全门禁，不自动提升生产。

## 版本与契约

- Backend、WEB 与 JS 业务候选继续使用统一三段式业务版本；首次原生基础包及 Lite 为 `6.8.0` / `5008000`。
- APK 的 `versionName`、`versionCode`、原生 `runtimeVersion` 由各客户端的原生基础包契约记录。原生能力不变时，业务版本可继续递增、原生基础包身份保持不变；只有原生兼容指纹变化并占用新基础包身份后才发布新 APK。
- `versionCode` 的唯一、递增与不可复用约束按 `applicationId` 分别成立；各应用仍使用既有 SemVer 公式。APK/OTA 制品不可覆盖，业务版本、源码 SHA、基础包身份和资源摘要均可追溯。
- 原生兼容检测必须覆盖原生依赖、Gradle/锁/校验、权限、插件、原生资源与 Kotlin/Java 代码；只改 JS 或业务版本不能误判为需要安装。
- OTA 资源先完成分发和摘要核对，再以短事务激活 manifest。失败不改变生效版本；重复发布同一不可变制品幂等，冲突内容拒绝。
- 测试与生产提升复用同一份导出 JS/资源；按目标环境生成、签署并登记 manifest，原生运行时和环境均隔离。

## Lite 行为

- 原生 View 设置与系统 WebView，移动业务 UI 由 WEB 提供；加载、离线/错误、重试、返回及环境设置由壳层保障。
- 文件选择/拍照、位置、下载、外部导航、必要诊断与安全能力按明确桥接接口适配。桥接仅接受受信任 HTTPS 来源和主框架消息，外链交由系统处理。
- 两款 APK 使用独立身份，各自仅接收同类型升级，不提供原生版与 Lite 的覆盖升级或应用内互转。用户更换客户端时先卸载当前版，再下载另一款安装；环境切换清理相关会话。APK 大小以 Release 包实测记录。

## 实施文件

- `e-report-lite/`：独立 Kotlin Android 工程、资源、桥接、测试、版本契约。
- Backend：AppRelease 的客户端类型、Liquibase 迁移、下载与发布服务、OTA 持久化/协议/签名/资源分发、权限及测试。
- WEB/原生 APP：发布中心和下载入口、OTA 检查/环境切换/版本显示、原生更新配置。
- `scripts/`、`.github/workflows/`、`security/`：版本/兼容指纹、OTA 打包签名发布、独立 Lite 构建、供应链审计和自动测试提升。
- 私有配置仓库：必要的 OTA 公钥/配置及服务资源；签名私钥保存在服务器管理私有目录与 Actions Secret。

## 验收

1. 原生版与 Lite 的发布、查询、下载、策略、对象路径均隔离；旧原生客户端的既有升级请求保持有效。
2. Lite Release APK 可签名构建、元数据一致，两种客户端不会相互升级，下载页明确卸载后更换；真实模拟器验证登录、工单页面、上传/预览/下载、环境切换和返回/错误恢复。
3. Expo SDK 57 的 OTA 原生基础包可安装、离线启动、校验并应用兼容更新；无效签名、错误运行时/环境、缺失资源和网络故障不替换可用版本。
4. 第二个纯 JS 测试候选能在保留同一原生基础包的条件下自动发布 OTA，并通过真实客户端确认业务版本变化；原生变动必须被兼容门禁识别。
5. Backend、WEB、APP 与 Lite 的相关测试、构建、锁/哈希、版本契约及供应链审计通过；云端生成制品、自动更新配置仓库并部署测试。

## 回滚与验证边界

- 客户端发布在 Backend 同时正确返回 NATIVE/LITE 身份后才开始，避免新 WEB 已就绪而 Backend 尚未完成迁移。自动镜像回滚仅发生在客户端发布前的部署 smoke 失败阶段。
- WEB 可回退上一不可变镜像。Lite 发布记录已生效后，Backend 必须保留按 edition 过滤的查询，不能直接回退到 `6.7.2` 或更早的二进制；首次迁移后异常优先发布修复版或回退到兼容 `6.8.x` 镜像。强制回到迁移前 Backend 需要先停止发布并显式撤销 Lite 发布状态，避免旧查询混入 Lite；不删除制品和历史记录。
- OTA 回退到已签署的兼容更新或内置基础包，保留审计记录；APK 使用更高版本修复。
- 原生构建、JS 导出、模拟测试和真实安装分别记录证据，不能相互替代。尚未完成的设备、流水线或环境验收明确记录，不报告为已上线。
